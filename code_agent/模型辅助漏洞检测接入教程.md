# 合同-5：纯模型检测接口接入教程

面向平台前后端工程师。现在支持三个场景：**指定一个或多个文件、分析整个项目、结合 GT 测指标**。同一个页面可选择静态检测或纯模型检测，两条检测链路独立执行。

## 1. 前端最少改什么

继续请求 `POST /api/run`，保留 `feature="vulnerability_detection"`，在 `feature_config` 中增加选择字段：

| 用户选择 | `detection_mode` | 执行内容 |
| --- | --- | --- |
| 静态检测 | `static`，也可不传 | 保持现有内置规则 / Cppcheck / Clang 流程 |
| 大模型检测 | `model` | 直接把源码送给模型，不运行上述三个检测器、不调用 Aider |

也可以直接调用新增接口 `POST /api/vulnerability/model`，请求格式相同；此接口固定为纯模型模式，可省略 `feature` 和 `detection_mode`。

**本次已实现上述接口。之前教程中的 `/api/agent/*` 多轮会话并非本次平台接入的必要步骤。** 不需要创建 Thread、推进 Run 或批准工具。纯模型接口不给模型任何工具，服务器按文件与上下文窗口分批发送源码。

平台可保留“使用 GT 测指标”复选框，并独立增加“静态 / 大模型”单选框。GT 是评估数据，不是另一种检测器。

## 2. 后端准备

在 `code_agent/` 目录安装依赖和本地分词器：

```bash
uv sync
uv run python scripts/install_deepseek_tokenizer.py
```

分词器仅用于调用前计算完整请求预算，即使使用其他供应商也需要安装。

例如使用仓库既有的 OpenRouter 模型配置：

```bash
export CODE_AGENT_PROVIDER="openrouter"
export CODE_AGENT_MODEL="anthropic/claude-sonnet-4.5"
export CODE_AGENT_API_BASE="https://openrouter.ai/api/v1"
export CODE_AGENT_CONTEXT_WINDOW_TOKENS="65536"
uv run python agent_web_api.py --host 127.0.0.1 --port 7860
```

启动前通过服务器部署环境配置 `OPENROUTER_API_KEY`，或者由平台后端在请求体的 `api_key` 中传入。不要把真实 Key 写进前端代码或 Git。上述模型 ID 是仓库示例，调用权限、余额与实际可用窗口由供应商决定；65536 是本地预算示例，不是模型能力声明。

模型默认配置沿用 `/api/bootstrap` 的 `runtime_default_model_config`，也可以通过请求的 `runtime_model_config` 显式指定。请求 Key 仅在内存中使用。

`project_dir` 必须是 **NaturalCC 服务器上的项目绝对路径**，接口不上传源码。平台与 NaturalCC 不在同一机器时，需要共享目录或先同步工程。`target_files` 是工作区内的文件路径，不能越出项目目录。

本次只新增模型检测能力，没有优化原静态检测耗时，也没有改动外部平台的页面。模型模式的实际时延仍需在服务器上实测。

## 3. 请求示例

### 3.1 检测指定文件

将以下内容保存为 `model-scan-request.json`，替换项目路径与目标文件：

```json
{
  "project_dir": "/srv/tasks/task-001/project",
  "target_files": ["src/thread.c", "src/ipc.c"],
  "feature": "vulnerability_detection",
  "runtime_model_config": {
    "provider": "openrouter",
    "model": "anthropic/claude-sonnet-4.5",
    "base_url": "https://openrouter.ai/api/v1",
    "context_window_tokens": 65536,
    "fallback_models": []
  },
  "feature_config": {
    "detection_mode": "model",
    "scan_scope": "targets",
    "scan_type": "high_risk",
    "auto_fix": false,
    "severity_threshold": "low",
    "max_findings": 100
  }
}
```

调用原入口：

```bash
curl --fail-with-body --no-buffer \
  -H 'Content-Type: application/json' \
  --data-binary @model-scan-request.json \
  http://127.0.0.1:7860/api/run
```

或调用独立入口：

```bash
curl --fail-with-body --no-buffer \
  -H 'Content-Type: application/json' \
  --data-binary @model-scan-request.json \
  http://127.0.0.1:7860/api/vulnerability/model
```

`/api/run` 同时兼容原来的表单请求：`target_files`、`feature_config`、`runtime_model_config` 分别传 JSON 字符串。独立入口使用 JSON 请求。

纯模型模式使用 `runtime_model_config`，不使用旧 Pipeline 顶层 `model` 字段；省略前者时使用服务启动默认配置。原表单中的 `analyzer=comprehensive`、编译上下文、`incremental` 等静态配置不会启动任何分析器。`auto_fix=true` 会被拒绝。

### 3.2 分析整个项目

仍使用上述请求，只修改：

```json
{
  "target_files": [],
  "feature_config": {
    "detection_mode": "model",
    "scan_scope": "project",
    "scan_type": "high_risk",
    "auto_fix": false,
    "max_findings": 100
  }
}
```

这是请求字段的修改片段，仍需保留 `project_dir`、`feature` 等顶层字段。

服务器递归收集 `.c/.h/.cc/.cpp/.cxx/.hpp/.java/.py/.js/.ts/.go/.php` 文件，跳过隐藏目录、`node_modules`、`venv`、`__pycache__`、`build/dist/out`。不读取普通 JSON 标签文件，配置的 GT 文件也会明确排除。符号链接不能扩大项目访问范围；发现越界源文件会拒绝请求。

每个文件独立调用模型，过长文件按本地 Token 预算分段并带相邻行重叠，最后汇总为一次任务结果。不会只读取每个文件的前一部分。模型没有跨文件工具检索能力，因此跨文件、跨分段问题可能遗漏；`coverage` 会公开这一限制。

### 3.3 使用 GT 计算指标

前端仍然可以读取 GT 来填充目标文件列表。在指定文件请求中追加：

```json
{
  "ground_truth_file": "ground_truth.json"
}
```

该片段放在 **`feature_config` 内**。GT 文件必须已经位于服务器的 `project_dir` 内；浏览器读取本机 GT 不会自动上传。保留原平台的上传 / 同步方式。GT 引用的文件必须包含在本次实际目标集合中。

执行顺序：

```text
后端冻结源码，校验 GT 格式、目标范围和 SHA-256
  → 只把源码和固定检测要求发给模型
  → 校验模型输出的类别、文件、行号、证据字段
  → 再次检查源码未改变
  → 后端把全部有效预测与 GT 对照，计算 TP/FN/FP/TN
  → 返回 findings / coverage / contract_statistics
```

GT 的 case、缺陷范围和答案不会进入模型消息，也不用于切分源码。GT 校验失败会在调用模型前返回 HTTP 422。

评分沿用原静态接口的 **同文件 + 同类别 + 行号落入 GT case 范围** 规则。用于评分的是全部有效预测，`max_findings` 只限制最终展示条数。GT 未标注的告警单独计数，不代表整个工程的准确率。

不传 GT 时仍正常检测，`contract_statistics.status="not_evaluated"`，没有 TP/FN/FP/TN 指标；这不表示检测失败。

### 3.4 用于“缺陷分析”页面

把 `scan_type` 改成 `frequent_defects`，模型只输出 `array_oob`、`string_overflow`、`null_pointer`。

合同-5 高危预警使用 `high_risk`，输出 `buffer_overflow`、`data_race`、`memory_leak`、`command_execution`。模型模式不执行合同-3 教学静态规则开关，也不能与旧静态成绩混合统计。

## 4. 前端怎么消费响应

响应仍为 `application/x-ndjson`：**每个非空行一个 JSON，不是 SSE**。沿用平台原有读取流方式；网络 chunk 可能包含半行或多行，须缓存到换行后再解析。

| `type` | 用途 |
| --- | --- |
| `start` | `mode=model`、目标文件数、模型配置 |
| `log` | 当前处理文件与文件序号 |
| `model.requested` | 调用序号、文件、原始行号范围、估算输入 Token |
| `model.reasoning.delta` | `text` 为供应商实际返回的推理文字 |
| `model.content.delta` | `text` 为本次调用的临时输出片段 |
| `model.usage_recorded` | 实际模型标识（若返回）、输入输出用量、估算校准信息 |
| `error` | 模型调用、格式校验、预算或源码变化失败 |
| `done` | 最终状态、报告及结构化 artifacts |

不同文件 / 分段的文本按 `file + call_index` 分组。推理文字字段是顶层 `text`，不是 Agent 会话事件的 `payload.text`。模型没有返回推理文字时，不生成该类事件，不能伪造 thought。

**结果表只使用 `done.artifacts.findings`，不要自己拼接多个分段的临时 JSON。**

成功的最终事件示意：

```json
{
  "type": "done",
  "status": "success",
  "mode": "model",
  "files_modified": [],
  "artifacts": {
    "detection_mode": "model",
    "scan_type": "high_risk",
    "findings": [],
    "coverage": [
      {"engine": "model", "status": "completed"},
      {"engine": "builtin", "status": "not_requested"},
      {"engine": "cppcheck", "status": "not_requested"},
      {"engine": "clang", "status": "not_requested"}
    ],
    "contract_statistics": {"status": "not_evaluated"}
  }
}
```

示例省略了详细字段。实际还返回：

- `report`：字符串报告，与原 Pipeline 结果一样可展示。
- `findings[]`：`file/line/column/category/function/reason/message/name/severity/analyzer/rule_id/snippet` 等；`analyzer="model"`。
- `coverage[0]`：完成 / 未完成文件、总行数、每段已分析的行号范围和能力限制。
- `finding_summary`：总候选数、展示数、是否截断。
- `usage`：模型调用数、估算与实际输入 Token、实际输出 Token、供应商报告的费用。
- `source_sha256`、`runtime_model_config`、`reported_models`：本次证据对应的源码和模型信息。
- `summaries`：模型对各文件 / 分段的说明。
- `contract_statistics`：有有效 GT 且任务完整成功时返回指标；失败不返回正式分数。

`confidence="model"` 和 `metric_eligible=true` 表示可参与评分的模型预测，不是漏洞已获独立证明。接口校验结构和源码位置范围，仍需人工核实语义证据。

## 5. 错误、预算与取消

- 请求不合法、路径越界、文件缺失、GT 哈希不匹配：HTTP 422，尚未发出模型请求。
- 模型调用或输出校验失败、Tokenizer 缺失、预算耗尽、源码被修改：流中返回 `error`，随后 `done.status="error"`。可能保留部分 findings，但 `contract_statistics.status="not_evaluated"`，不能显示成“无漏洞”或正式得分。
- 整个项目成功意味着已处理本次枚举到的全部受支持源码；不保证模型能发现所有漏洞。
- 连接中断后停止后续模型调用；已在途的供应商读取可能要等本次读取返回或超时才释放。平台取消任务时需要关闭到 NaturalCC 的上游连接，不能只断开浏览器连接。
- 本接口是与原 `/api/run` 一样的单次流式任务，不创建持久化 Agent Run，没有 `/step`、断点重连或后台结果查询。平台负责保存事件及最终结果；请求中途断开不能直接当作检测成功，也不要自动反复重发产生重复消费。

可在 `feature_config.model_limits` 覆盖以下默认预算：

```json
{
  "max_files": 500,
  "max_file_bytes": 2000000,
  "max_total_bytes": 50000000,
  "max_model_calls": 500,
  "max_input_tokens": 2000000,
  "max_output_tokens": 200000,
  "output_tokens_per_call": 4096,
  "max_seconds": 1800
}
```

`max_input_tokens` / `max_output_tokens` 是任务累计预算，`context_window_tokens` 是每次请求窗口。每次请求都使用固定本地分词器计算消息、供应商开销、输出预留和安全余量，并根据已报告用量保守校准后续估算。单行仍超限时明确失败，不会退回字符估算或静默截断。

`analysis_timeout_seconds` 兼容旧表单，作为 `max_seconds` 的默认值；显式 `model_limits.max_seconds` 优先。模型预算配置中的未知字段会被拒绝，避免拼写错误悄悄变成默认预算。

## 6. 最小联调顺序

1. 不带 GT，选择一个小文件，确认 `model.requested`、实际用量事件与 `done.status=success`。
2. 选择两个文件，核对 `completed_files` 和每个文件的行号。
3. 使用匹配源码的 GT，检查 `contract_statistics.status=evaluated` 和各类别指标。
4. 改成 `scan_scope=project`，检查文件数、被忽略目录及预算是否符合预期。
5. 使用无效 GT / 过小预算验证错误展示，确认不会被误报为“未发现漏洞”。

不需要先启动三个静态检测器。静态模式不受影响，继续按原参数调用。完整回归测试使用替身模型，不产生模型费用；本次实现没有在甲方服务器或真实付费模型上验证速度和检测指标。

## 7. 与既有 Contract-5 Web 评测的区别

`scripts/benchmark_contract5_web.py` 仍是旧的多轮 Agent + 内置工具审计协议，未改成纯模型。它按函数或行号匹配，不能把那份成绩直接与本接口的 case 行范围评分混为一谈。

新增纯模型接口使用 `security_contracts.evaluate_contract` 的原平台评分规则，与静态接口共用 GT 格式。联调和对比时请分别记录检测模式、模型、源码哈希、完整 coverage 和评分口径，不覆盖旧实验结论。
