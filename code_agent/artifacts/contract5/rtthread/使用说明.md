# 合同第 5 项 · 操作系统底层程序高危代码检测数据集 · 使用说明

本包提供一整套操作系统底层程序（RT-Thread v5.2.1 子集）及其 ground truth，用于测试"缓冲区溢出、多线程竞争、内存泄漏、命令执行漏洞"四类高危代码的检测与预警能力。

> 本包含全部答案。发给被测方或学生时**只给 `project/` 和 `prompt.md`**，其余文件都写明了缺陷位置。

## 一、包内容

| 路径 | 说明 |
|---|---|
| `project/` | **被测工程**：注入缺陷后的完整 RT-Thread 工程，332 个文件、108,524 行源码。这是交给检测系统的工作区。 |
| `ground_truth.json` | **真值**：每一条测试对应工程里的哪个文件、哪个函数、哪一行，是什么类别的缺陷，或该文件本身没有缺陷。 |
| `manifest.json` | 332 个文件逐一的 SHA256，用于校验工程未被篡改。 |
| `prompt.md` | 发给检测系统的命令提示文本模板，`{file}` 替换为待检文件路径。 |
| `dataset_spec.json` | 上游仓库与固定提交、复制的子树清单、无缺陷文件清单。 |
| `injections/*.json` | 四类缺陷的注入锚点与标签（出题源文件）。 |
| `scripts/` | 重建/校验数据集与执行测试的脚本。 |
| `使用说明.md` | 本文件。 |

## 二、规模与注入分布

- 工程：RT-Thread v5.2.1，固定提交 `97893c004c65`，332 个文件，源码 108,524 行。
- 待检文件：34 个，合计 **29,821 行**（满足不少于 1 万行的要求）。其中 20 个含缺陷、14 个完全无缺陷。
- 注入缺陷：4 类 × 10 处 = **40 处**；另配 43 处安全对照函数（外形相似但确实安全），用于测误报。

| 类别 | CWE | 缺陷 | 难度 easy/medium/hard | 安全对照 |
|---|---|---:|---|---:|
| 缓冲区溢出 | 787 | 10 | 4/4/2 | 10 |
| 多线程竞争 | 362 | 10 | 4/4/2 | 10 |
| 内存泄漏 | 401 | 10 | 4/4/2 | 12 |
| 命令执行漏洞 | 78 | 10 | 4/4/2 | 11 |

## 三、ground truth 怎么读

`ground_truth.json` 采用与产品检测接口一致的格式，可直接作为 `vulnerability_detection` 的 `ground_truth_file` 传入（配合 `scan_type: "high_risk"`），由 `security_contracts.evaluate_contract` 直接算出 TP/FN/FP/TN 与各项比率，无需另写转换。

顶层结构：

| 字段 | 含义 |
|---|---|
| `schema_version` | 固定为 `1`。 |
| `scan_type` | 固定为 `high_risk`，与检测接口的扫描类型对应。 |
| `source_sha256` | **要检测的文件清单**：文件路径 → SHA256。共 34 个文件。 |
| `detection_files` | 同一批文件的详情：路径、行数、散列、`verdict`（`vulnerable` 有缺陷 / `clean` 无缺陷）、缺陷数、对照数、涉及类别。 |
| `cases` | **每一条测试**，见下。 |
| `line_totals` | `detection_files` 合计行数与工程源码总行数。 |
| `project` | 上游仓库、固定提交、复制的子树。 |
| `categories` | 四类的缺陷数、对照数与难度分布。 |
| `line_rule` / `scoring_rule` / `metrics` | 行数要求、计分规则与指标公式。 |

`cases` 里每条测试对应工程里的一个函数：

```jsonc
{
  "case_id": "rt-thread-buffer_overflow-defect-01",  // 唯一编号
  "site_id": "BOF-01",                 // 对应 injections/ 里的注入条目
  "project": "rt-thread",
  "category": "buffer_overflow",       // 四类之一，与告警类别比对
  "cwe": 787,
  "expected": "defect",                // defect = 注入缺陷；control = 安全对照
  "function": "rt_kprintf",            // 在哪个函数
  "file": "src/kservice.c",            // 对应工程里的哪个文件
  "line_start": 359,                   // 函数起止行，命中判定用
  "line_end": 385,
  "defect_line": 373,                  // 缺陷（或对照焦点）所在行
  "defect_code": "length = rt_vsnprintf(rt_log_buf, sizeof(rt_log_buf) + 64, fmt, args);",
  "difficulty": "easy",
  "description": "……什么毛病……",
  "trigger": "……什么条件触发……",
  "fix": "……正确改法……"
}
```

`source_sha256` 中出现、但 `cases` 里没有任何条目的文件，就是完全无缺陷的对照文件；对这些文件的任何同类告警都计为误报。

## 四、计分口径

计分单位是 **site**：一个被注入缺陷的函数，或一个安全对照函数。检测结果的每条告警含 `category`、`function`、`line`；**告警类别与 site 相同，且函数同名或行号落在该函数的 `[line_start, line_end]` 内**，即判为命中。

| 真值 \ 预测 | 命中 | 未命中 |
|---|---|---|
| defect（注入缺陷） | TP | FN |
| control（安全对照） | FP | TN |

- **预警准确率** = TP/(TP+FP) ← 合同指标，要求 > 90%
- **误报率** = FP/(FP+TN) ← 合同指标，要求 < 8%
- 检出率 = TP/(TP+FN)
- 正确率 = (TP+TN)/N

落在非 site 函数上的告警记为"范围外告警"，单独统计，不进入上述指标。另有文件级判定：某文件出现任意告警即视为"预测该文件有漏洞"，与其 `verdict` 比较。

## 五、怎么用

**校验数据未被篡改**（不需要联网）：

```bash
python scripts/build_contract5_dataset.py --verify
```

**只评估静态检测层**（不调用任何大模型、不联网）：

```bash
python scripts/measure_contract5_static.py            # 汇总表
python scripts/measure_contract5_static.py --misses   # 逐条列出漏报与误报
```

**跑完整的模型检测**：需要启动 Web Agent 后端并配置模型，逐个待检文件建立独立会话，详见 `scripts/benchmark_contract5_web.py` 的说明。`--print-prompts` 可在不联网的情况下查看每个文件实际发出的提示词。

## 六、两个必读的坑

**1. 读取工具会静默截断。** 被测 Agent 的 `workspace.read` 默认只返回前 20000 个字符且没有 offset 参数，超出部分被丢弃而 Agent 不会察觉。本数据集最大文件 `src/ipc.c` 有 138,342 字符——按默认上限，40 处缺陷中有 16 处物理上够不着，检出率天花板只有 60%。`prompt.md` 已要求显式传入 `max_chars: 400000` 并检查 `truncated` 字段。换模型或改提示词后，请从测试产生的 `runs/*.json` 中取 `workspace.read` 的 `max_chars` 实参与文件字节数比对，确认不是部分读取。

**2. 模型上下文要够大。** 完整读取 `src/ipc.c` 约 4 万 token，加上工具结果与多轮对话，单次请求可达 4 万 token 以上。上下文窗口小于 6 万 token 的模型跑不了最大的那几个文件，会直接报上下文超限。
