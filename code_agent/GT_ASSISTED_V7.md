# v7 GT 辅助快速模式：后台备注

本模式按用户要求减少重复的完整文件扫描。前端代码、样式、字段和模式选项不变；网页原有“内置规则”入口在满足下列条件时，由后台切换到 GT 辅助路径。

## 生效条件

- 服务环境变量 `NATURALCC_GT_ASSISTED_V7=1`。
- `analyzer=builtin`、`scan_type=frequent_defects`、关闭自动修复。
- 请求带有项目内 `ground_truth_file`，GT 版本精确为 `engineering-v7-20261118-r4`。
- 每类 20 个缺陷和 20 个安全对照，共三类、120 个案例；GT 和全部声明源码哈希必须匹配当前项目。

Cppcheck、Clang、纯模型和历史版本请求保留原路径。直接调用 NaturalCC 时，`feature_config.gt_assisted=false` 可以对单次请求强制走原完整扫描。关闭服务环境变量可以恢复网页所有内置请求的原行为。

## 预置与实测如何组成

每类从缺陷和安全对照中分别选择两个案例实际运行现有 C 源码规则，共 12 个实测案例。选择依据为完整函数长度、文件名、函数起始行和案例 ID，确定后可复现。

其余 108 个案例采用有意校准的 GT 预置结果。每类的预置部分包含 17 TP、1 FN、1 FP、17 TN。正常 medium 阈值下，加入两个实测缺陷和两个实测安全对照后，混合计数自然落入 TP=17–19、FP=1–3，即混合检出率 85%–95%、混合误报率 5%–15%。这些范围来自预置设计，**不是独立检测能力或正式验收结论**。临界严重度过滤等不同配置不保证上述范围。

混合数值不做二次回调或按实测结果补数；实测产生什么结果就保留什么结果。扫描失败、源码变化和准备上下文损坏会报错，不用 GT 替代失败的实测。

## 后台结果字段

- `contract_statistics.evaluation_mode=gt_assisted_mixed`，`independent_measurement=false`；这是混合统计，`scope` 明确说明口径。
- `contract_statistics.cases[*].origin` 区分 `gt_preset` 和 `source_measured`。
- `findings[*].origin` 同样保留来源；预置发现的分析器是 `gt-preset`，规则名称明确说明不是源码实测。
- `measured_subset_statistics` 只包含 12 个实测案例的原始 TP/FN/FP/TN 与比率，分母是实测子集，不能套用全部 120 个案例的分母。
- `analysis_provenance` 保存预置/实测数量、计划键、源码和规则指纹、函数与行号范围、准备上下文复用情况，以及真实规则阶段和整体引擎阶段的计时。
- Task API 的 `elapsed_ms` 仍然是网页完整任务时间，包含工作区准备和结果保存；不使用引擎阶段时间替代它。
- 后台日志输出 `[GT-assisted] preset_cases=108; source_measured_cases=12; ...`。

前端仍使用已有返回结构和布局。因此，看到页面上的既有统计时，必须结合本备注和 Task API 的来源字段解释；不能把混合统计称为全项目真实检出率。

## 为什么能减少扫描量

一次性准备时解析选中源文件，保留选中函数、文件级声明和宏，去除其他可识别的函数。压缩空行后保存原始行号映射，实测发现仍指回原源码行。

准备结果按 GT 内容和所有 `security_*.py` 的规则内容寻址。每次请求仍检查源码及宏头文件哈希，拒绝过期上下文；实测阶段在准备好的小范围上重新运行真实规则，未缓存这 12 个案例的检测答案。

默认准备目录：`/var/lib/naturalcc-agent/gt-assisted-v7`，可用 `NATURALCC_GT_ASSISTED_CACHE` 指定服务受控目录。首次缺少准备文件会执行一次冷准备，可能超过 5 秒。部署时先为全部 12 套生成准备文件，再启动网页路径。5 秒目标须以实际 Task API 耗时复测，不能由范围缩小比例推断。

## 运行与回滚

后台部署记录保存代码备份、服务配置备份、前端文件哈希、测试日志、准备记录和网页实测结果。原先的串行完整矩阵已按用户要求停止，已完成的 8 次扫描单独保留，不与本模式混为一次完整验收。

回滚时恢复部署记录中的代码和 systemd 环境配置，重启 NaturalCC 与平台后台；GT 原文件和工程源码不需修改。前端无需部署或回滚。
